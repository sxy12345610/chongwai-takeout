# 重外校园外卖平台 · 支付架构规划

> 文档版本：v0.1（第一阶段：架构审计与设计）
> 目标渠道：**微信小程序支付（微信支付 API v3）**
> 当前阶段：**仅做流程与接口设计，不接入真实支付、不填写任何真实密钥/证书/商户号**
> 重要前提：现有项目为「模拟支付」，本文档描述的是未来接入真实支付的目标方案

---

## 1. 现状与前提

### 1.1 现有实现

- `Checkout.vue` 中「提交订单（模拟支付）」：直接创建订单并标记为待接单，**没有任何真实支付调用**。
- 订单金额完全由前端计算（商品小计 + 配送费 - 满减）。
- 项目为纯前端 Vue 3 + LocalStorage，**没有后端**，无法安全持有支付密钥。

### 1.2 已知条件与待确认

| 事项 | 状态 |
| --- | --- |
| 微信小程序账号 | **已有**（用户说明） |
| 小程序 AppID | 待确认（不写入文档） |
| 微信支付商户号（mchid） | **待确认，可能没有** |
| 商户 API 证书 / APIv3 密钥 | 待确认 |
| 小程序与商户号是否已关联 | 待确认 |
| 是否已有对公账户 / 主体资质 | 待确认（不编造） |
| 是否保留支付宝渠道 | 待确认（目标形态仅微信小程序，首版按仅微信设计） |

> 若没有商户号，可先完成「下单 → 待支付 → 后端标记未支付」的完整业务闭环，支付渠道以**开关关闭**的方式预留，不伪造支付成功。

## 2. 总体设计原则

1. **金额只由服务端计算**：客户端不得上传金额；支付金额取 `orders.total_cents` 之和。
2. **支付与订单分离**：`payments` 记录渠道交易，`orders` 只关心业务状态，通过 `payment_orders` 分摊。
3. **客户端结果不可信**：`wx.requestPayment` 成功回调只代表用户完成操作，最终以服务端查单/异步通知为准。
4. **回调必须验签 + 解密 + 核对金额 + 幂等**。
5. **密钥只存在服务端**：APIv3 密钥、商户私钥、证书序列号等通过环境变量/密钥文件注入，禁止进入前端、Git、日志。
6. **一次结算可拆多单**：多商家购物车生成多笔订单，共用 `checkout_group_no`，一次支付。
7. **可降级**：`PAYMENT_MODE=disabled` 时下单后订单为「待支付」，不产生虚假支付成功。

## 3. 微信小程序登录流程

```
小程序                         后端                         微信服务器
  │  wx.login()                  │                              │
  │ ── code ───────────────────▶ │                              │
  │                              │ ── code2Session(appid,secret,code) ─▶
  │                              │ ◀── openid / session_key / unionid ──
  │                              │ 查/建 users（openid 唯一）      │
  │                              │ 签发 JWT（access + refresh）    │
  │ ◀── accessToken/refreshToken/user ──                         │
  │                              │                              │
  │ 后续请求 Authorization: Bearer <accessToken>                 │
```

要点：

1. `code` 一次性，5 分钟内有效，服务端立即换取，不落库。
2. `session_key` **不返回给客户端**，仅服务端保存（如需解密手机号/敏感数据）。
3. 首次登录创建用户，昵称/头像可由前端补充后 `PATCH /users/me`。
4. 是否需要强制绑定手机号 **待确认**；若需要，使用微信手机号快速验证能力（`getPhoneNumber`），后端解密。
5. JWT 建议：Access Token 2 小时，Refresh Token 30 天并轮换。

## 4. 微信支付后端预支付流程

### 4.1 时序

```
小程序                 后端                              微信支付
  │ 提交订单 POST /orders   │                                  │
  │ ─────────────────────▶ │ 事务：拆单、扣库存、写订单        │
  │ ◀── checkoutGroupNo ─── │                                  │
  │                        │                                  │
  │ POST /payments/wechat/prepay                              │
  │ ─────────────────────▶ │ 1. 校验订单归属/状态/金额         │
  │                        │ 2. 创建 payments(PENDING)         │
  │                        │ 3. 统一下单 /v3/pay/transactions/jsapi ─▶
  │                        │ ◀── prepay_id ────────────────────
  │                        │ 4. 生成小程序调起支付签名          │
  │ ◀── timeStamp/nonceStr/package/signType/paySign ──────────│
  │                                                           │
  │ wx.requestPayment(...)                                    │
  │ ────────────────────────────────────────────────────────▶ │
  │ ◀── success / fail / cancel ──────────────────────────────│
  │                        │                                  │
  │ GET /payments/:id/status（轮询）                          │
  │ ─────────────────────▶ │ 查本地或主动查单                  │
```

### 4.2 预支付请求要点

- 接口：`POST /payments/wechat/prepay`
- 入参：`checkoutGroupNo` 或 `orderIds[]`；**不含金额**。
- 服务端：
  1. 校验订单属于当前用户、状态为待支付、未关闭；
  2. 汇总金额（分）；
  3. 生成商户订单号 `out_trade_no`（全局唯一，建议 `CW` + 时间 + 随机）；
  4. 调微信 JSAPI 下单，`payer.openid` 取当前用户；
  5. 保存 `prepay_id`，返回小程序调起参数。
- 金额校验：微信侧金额与本地 `payments.amount_cents` 必须一致，否则拒绝。

### 4.3 小程序调起参数

```json
{
  "timeStamp": "1732000000",
  "nonceStr": "随机字符串",
  "package": "prepay_id=wx...",
  "signType": "RSA",
  "paySign": "服务端签名结果"
}
```

> 签名使用商户 API 私钥（仅服务端），不得下发给客户端。

## 5. 支付状态验证与异步回调

### 5.1 回调处理流程

```
微信支付 ── POST /payments/wechat/notify ──▶ 后端
  1. 读取原始 body（保留字节，用于验签）
  2. 验证签名（平台证书/公钥、时间戳、随机串、签名）
  3. 解密 resource（AES-256-GCM）
  4. 校验：appid、mchid、out_trade_no、amount.total、trade_state
  5. 幂等：按 out_trade_no 行锁查询 payments
       - 已 PAID → 直接返回 SUCCESS
       - 金额不一致 → 记录告警，返回失败
  6. 事务：
       - payments → PAID，写 provider_trade_no / paid_at / raw_notify（脱敏）
       - payment_orders 关联的订单 → 待接单
  7. 返回 { code: "SUCCESS", message: "成功" }
```

### 5.2 回调安全要求

1. **必须验签**，禁止跳过；平台证书需定期更新。
2. **必须解密**，不得信任明文参数。
3. **必须核对金额与商户号**，防止金额篡改。
4. **必须幂等**，微信会重复通知。
5. 回调接口**不做用户鉴权**，但必须限制来源并记录审计日志。
6. 返回非 `SUCCESS` 会触发微信重试，避免误返回成功。

### 5.3 主动查单补偿

- 回调可能丢失，增加定时任务扫描 `PENDING` 且超过 2 分钟的支付单，调用微信查单接口。
- 查单结果与回调走同一套状态更新逻辑（幂等）。
- 前端轮询 `GET /payments/:paymentId/status`，不直接信任 `wx.requestPayment` 的 success。

## 6. 支付成功后的订单状态更新

```
payments.PENDING → PAID
        ↓（同一事务）
orders.status：待支付 → PENDING（待接单）
        ↓
商家接单 → PREPARING
        ↓
配送员取餐 → DELIVERING
        ↓
配送员送达 → COMPLETED
```

规则：

1. **未支付订单不允许商家接单**。
2. 支付成功只更新「支付状态 + 订单进入待接单」，不改配送状态。
3. 多商家拆单时，组内所有订单一起变为待接单。
4. 若组内某订单已被取消（极端并发），需在事务内校验，必要时对差额发起退款。

## 7. 支付失败、取消与超时

| 场景 | 处理 |
| --- | --- |
| 用户取消支付 | `wx.requestPayment` 返回 fail/cancel；支付单保持 `PENDING`；订单保持「待支付」，允许重新支付 |
| 支付失败（余额不足等） | 记录失败原因（脱敏）；支付单 `FAILED` 或保持 `PENDING` 允许重试（**策略待确认**） |
| 支付超时（默认 15 分钟） | 定时任务关闭支付单（`CLOSED`），取消关联订单，恢复库存 |
| 回调金额不一致 | 不更新订单，记录 P0 告警，人工介入 |
| 重复支付 | 以 `out_trade_no` 幂等；若用户对同一订单组重复创建支付单，需关闭旧单 |
| 支付成功后商家拒单 | 订单 `CANCELLED`，自动发起全额退款 |
| 退款失败 | 退款单 `FAILED`，支持后台重试；订单保持取消态 |

**超时时间建议**：下单后 15 分钟未支付自动关单（可配置）。

## 8. 多商家平台的商户结算方案

> 这是本项目最需要提前确认的架构问题。以下为三种可选模式，**均待确认**，本阶段不做实现。

### 方案 A：平台统一收款（普通商户模式）

```
学生 ──支付──▶ 平台商户号（单一 mchid）
                    │
                    └── 线下/定期结算给各商家
```

- 优点：接入最简单，只需一个商户号；所有订单资金先进入平台。
- 缺点：平台承担资金归集与结算，涉及二清合规风险；需要人工/对账系统给商家打款。
- 适用：比赛演示、校内小规模试点。

### 方案 B：微信支付服务商 + 分账

```
学生 ──支付──▶ 服务商商户号 ──分账──▶ 各商家子商户号
```

- 优点：合规性较好，支持自动分账；适合多商家平台。
- 缺点：需要服务商资质、子商户进件、分账比例配置，接入成本高。
- 待确认：是否具备服务商资质；各商家是否能完成子商户进件。

### 方案 C：商家直连（一商家一商户号）

```
学生 ──支付──▶ 商家自己的商户号
```

- 优点：资金不经过平台，合规压力最小。
- 缺点：一次结算跨多个商家时需要**多次支付**，体验差；每个商家都要有商户号。
- 与本项目「一次结算拆多单、一次支付」的设计冲突，需改成按商家分别支付。

### 建议

- **比赛/演示阶段**：方案 A，且支付开关可关闭，重点展示业务闭环。
- **真实运营阶段**：优先评估方案 B；若资质不足，再考虑方案 A + 人工结算。
- 无论哪种方案，`payments` / `payment_orders` / `refunds` 的数据结构都能复用，仅结算层不同。

## 9. 数据与安全清单

| 项目 | 要求 |
| --- | --- |
| 商户 API 私钥 | 仅服务端文件/密钥管理，权限最小化，不入 Git |
| APIv3 密钥 | 仅服务端环境变量 |
| 平台证书 | 定期下载更新，校验序列号 |
| AppSecret | 仅服务端，绝不写入小程序代码 |
| 日志 | 不记录完整回调密文、密钥、openid 可脱敏 |
| 数据库 | `raw_notify` 存脱敏后的关键字段，不存完整敏感报文 |
| 幂等 | `out_trade_no`、`out_refund_no` 唯一索引 |
| 对账 | 每日下载微信账单，与 `payments` 核对（后续阶段） |

## 10. 与现有前端的关系

- 现有 `Checkout.vue` 的「模拟支付」在迁移后必须替换为：
  1. `POST /orders` 创建订单；
  2. `POST /payments/wechat/prepay` 获取调起参数；
  3. `wx.requestPayment`；
  4. 轮询支付状态。
- 迁移期间可保留「模拟支付」作为演示模式，但必须**与真实支付代码隔离**，通过环境开关控制，禁止在生产环境误用。
- 现有前端计算的金额仅用于展示，提交订单时不再上传金额。
